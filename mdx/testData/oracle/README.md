# MDX mdast oracle

This directory holds an **offline, re-runnable oracle** for the MDX plugin's
parsing tests. Each `<Name>.mdast.json` is the normalized [mdast][mdast] tree
that the **canonical MDX toolchain** (the same one that powers the AST explorer
on [mdxjs.com][mdxjs]) produces for the matching `../parsing/<Name>.mdx`
fixture.

## Why this exists

The MDX acceptance tests historically referenced the canonical mdast in
hand-written KDoc prose. That prose was never verified against the real
compiler and had already drifted (e.g. it described front matter incorrectly).
This oracle replaces "trust the prose" with "diff against a real parse": the
artifacts are generated by the actual `@mdx-js/mdx` remark pipeline, checked in,
and regenerable on demand.

## What the oracle is *not*

It is a **structural reference**, not a byte-for-byte expectation of the
IntelliJ PSI. The IntelliJ MDX plugin parses a single file into **two** PSI
trees (a Markdown PSI tree plus a stitched JS/JSX PSI tree linked through the
template-language infrastructure; see `../../.ai/pipeline.md` for background
when present). The mdast
oracle is a **single recursive tree** with a different vocabulary
(`mdxJsxFlowElement`, `mdxjsEsm`, `yaml`, `code`, ...). A Kotlin test should use
the oracle to assert *structural equivalence* (node nesting, kinds, key
fields), never a literal string match against the PSI dump.

## Regenerating

From `contrib/mdx/testData`:

```sh
npm ci                       # install pinned toolchain (first time / CI)
npm run generate:mdast       # regenerate every parsing/*.mdx -> oracle/*.mdast.json
```

`npm ci` installs the exact versions from `package-lock.json` without touching
the lockfile. Use `npm install` **only** when you intend to bump the toolchain
(it may rewrite the lock).

The generator can be pointed at other fixture directories:

```sh
node oracle/generate-mdast.mjs --in <inputDir> --out <outputDir> [--positions]
```

- `--in` (default `parsing`): directory scanned for `*.mdx`, resolved relative
  to `testData/`.
- `--out` (default `oracle`): directory that receives `*.mdast.json`.
- `--positions`: include unist `position` ranges (omitted by default for
  stability; useful for debugging drift).

The generator globs the input directory **at run time**, so newly added
`*.mdx` fixtures are picked up automatically on the next run — no code change
needed.

## Toolchain (pinned in `../package.json` / `../package-lock.json`)

| Package             | Version | Role                                             |
|---------------------|---------|--------------------------------------------------|
| `unified`           | 11.0.5  | processor host                                   |
| `remark-parse`      | 11.0.0  | Markdown -> mdast                                |
| `remark-gfm`        | 4.0.1   | GFM tables / strikethrough / task lists          |
| `remark-frontmatter`| 5.0.0   | YAML/TOML front matter -> `yaml` / `toml` nodes  |
| `remark-mdx`        | 3.1.1   | MDX JSX / ESM / expression nodes (mdast layer)   |

The generator builds a **remark-only** `unified` processor and runs
`parse()` + `runSync()`. It deliberately avoids `@mdx-js/mdx`'s
`createProcessor()`, whose transformer chain continues past mdast into hast and
then estree/JS; `runSync()` on that processor would leave a *non-mdast* tree.
As a guard, the normalizer throws if it ever encounters a hast node
(`element` / `doctype`).

## Output format & normalization rules

Each file is (object keys are sorted alphabetically at every level, so
`mdast` / `parseError` precede `source`):

```json
{
  "mdast": { "children": [ ... ], "type": "root" },
  "source": "parsing/<Name>.mdx"
}
```

or, when the MDX toolchain rejects the fixture:

```json
{
  "parseError": { "column": N, "line": N, "reason": "...", "ruleId": "..." },
  "source": "parsing/<Name>.mdx"
}
```

Normalization keeps the tree small and stable:

- **`type` is always kept.** `children` arrays are recursed into, preserving
  order.
- **A small whitelist of structural fields is kept per node type**, e.g.
  `depth` (heading); `lang` / `meta` / `value` (code); `value` (text,
  inlineCode, yaml, toml, html, mdxjsEsm, mdx*Expression); `ordered` / `start`
  / `spread` (list); `checked` / `spread` (listItem); `url` / `title` / `alt`
  (link / image); `identifier` / `label` / `referenceType` (references and
  definitions); `align` (table); `name` (mdxJsx* elements).
- **JSX attributes are normalized** into `{type, name, value}`. String
  attribute values stay strings; expression attribute values keep their raw
  `{...}` source text as `{type: "mdxJsxAttributeValueExpression", value}`;
  spread attributes keep their `value` source text. The bulky `data.estree`
  payload is dropped.
- **`position` is dropped** (unless `--positions`), and **`data` is always
  dropped** (it carries verbose estree/acorn output that is not part of the
  structural oracle).
- **Determinism:** input files are sorted; object keys are sorted recursively;
  output uses 2-space indentation with a trailing `\n`; no timestamps or
  absolute paths appear in the JSON. Re-running over unchanged inputs is a
  no-op (no git diff).

## Notable MDX-spec divergences captured

These confirm why the prose oracle was unreliable; the real toolchain behaves
differently from plain Markdown / from the current IntelliJ parser:

- **Front matter** (`ParsingFrontMatter`) parses to a `yaml` node, **not** a
  thematic break.
- **Autolinks** (`ParsingAutolink`, `<https://example.com>`) are **invalid
  MDX** — `<` starts JSX, so this is recorded as a `parseError`.
- **HTML comments** (`ParsingHtmlComment`, `<!-- -->`) are **invalid MDX** —
  recorded as a `parseError` (MDX expects `{/* */}`).
- **Indented code** (`ParsingIndentedCode`) is **disabled** in MDX — the
  indented lines parse as a `paragraph`, not a `code` node.
- **Line-leading `import` / `export`** (`ParsingImportInProse`) is always
  treated as ESM, so a line that *starts* with `import`/`export` but is not
  valid JavaScript is a `parseError` (acorn), **not** prose. Only `import`
  used mid-sentence stays a `paragraph`.
- **Markdown inside JSX** (`ParsingMarkdownInJsx`) is parsed recursively: a
  `Callout` `mdxJsxFlowElement` contains a real `heading` and `list`.

## How a future Kotlin test could consume this

Sketch (not yet implemented):

1. Load `oracle/<Name>.mdast.json` (e.g. with the platform JSON reader).
2. If it has a `parseError`, assert the IntelliJ parser also flags an error /
   produces error PSI for that construct (or document the intentional
   divergence).
3. Otherwise walk the `mdast` tree and assert the IntelliJ PSI exposes a
   structurally equivalent shape — same nesting of headings/lists/code/JSX/ESM,
   same key fields (heading depth, code lang + verbatim value, JSX element
   names, front-matter body) — mapping mdast node kinds onto the two-root PSI
   vocabulary. This is an equivalence assertion, **not** a literal dump
   comparison.
